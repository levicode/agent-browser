# Native extension inventory

Review basis: the 13-file patch at `e2e/patches/agent-browser-exact-refs.patch`, applied to agent-browser `1165952d74ceed98fdc2dd97190ad41f44dd0e24` (0.39.1). The reviewed extension identifies itself as `0.39.1-e2e.4`. This is a source review, not new execution evidence. The inventory intentionally includes tests in the patch's line count; that count is not the size of the production-only divergence.

The original extension is the review basis. This migration preserves its strict guarantees, incorporates upstream through the exact base in `upstream.json`, formats touched Rust code, and completes version/documentation/release hygiene. Behavioral profile isolation and capability discovery remain future, separately tested changes. Do not remove a guarantee merely because its implementation touches many call sites.

## Native requirements within the selected strict contract

These requirements are necessary for the strict contract chosen by this implementation, not universal requirements for every e2e engine or reasons that all agent-browser users need a fork. An adapter-only pre-check cannot prevent native-internal rebinding, a second input or unowned lifecycle work. Reuse existing upstream primitives and prefer precise additive operation arguments where those preserve the selected contract. Exact-reference checking still does not make coordinate input atomic.

## Incidental/default-impact divergence to contain

The current patch is not wholly opt-in. Preserve its tested strict behavior first, then reduce unrequested effects on stock callers in a separate semantic change.

| Impact | Evidence in the frozen patch | Recommended boundary |
| --- | --- | --- |
| All native `fill` calls now use a DOM value setter and synthetic `InputEvent`, not upstream's `Input.insertText` path. | `interaction.rs::fill` is replaced without an operation-specific boundary; `actions.rs::handle_fill` invokes it for every native call. The adapter explicitly documents the `event.isTrusted` difference. | Replace the blanket setter with the single shared upstream text-input implementation and narrow supported value-type setters. Do not silently claim trusted text-entry parity. |
| Default select matching changes. | `interaction.rs::select_option` removes whitespace normalization/text-content fallback, rejects multiple matches, checks disabled options, and emits input plus change. The parser still defaults to `auto`. | Explicit strict modes retain current e2e semantics. Decide and test `auto` separately; do not accidentally change stock default matching while adding `--label` and `--index`. |
| All snapshot refs lose role/name fallback, and all cursor/frame failures become hard failures. | `RefMap::add_with_frame` changes the default; `take_snapshot` drops `unwrap_or_default` and previously ignored child errors. | Good safety fixes may be accepted globally by upstream. Until that decision, document them as deliberate fork defaults or scope them explicitly. Never restore fallback or incomplete-success behavior for the strict adapter. |
| Legacy check/uncheck fallback is removed globally. | `interaction.rs::check/uncheck` replace `js_click_checkbox` for all callers. | Prefer upstreaming the at-most-once fix. If legacy compatibility is necessary, use shared upstream primitives with an explicit no-replay operation contract; do not retain duplicated old/new implementations. |
| New public commands lack complete upstream-facing documentation/parity. | Patch changes help only for scope flags; no corresponding changes to `mcp.rs`, main README, skill references, docs pages or schema. `ref` is added to the chat command allowlist. | Document the extension surface, its intentional MCP omissions or matching MCP tools, and test parser parity. Do not accidentally expose a command through chat while leaving its supported contract unspecified. |
| Version and release policy are inherited incompletely. | Patch bumps root/Cargo versions, not dashboard version. Upstream CI includes `check-version-sync.js`. Upstream release workflow publishes on main pushes when the version differs from npm. | Synchronize all versioned components; guard upstream publication and require a separate approved fork release. Keep npm/package identity decisions separate from native semantic changes. |
| Compressed additions create avoidable merge/style churn. | Many new functions/tests are single-line or densely packed; the e2e native build does not run upstream rustfmt/clippy gates. | Format only touched extension code in a distinct mechanical commit, then run upstream format/lint gates. Avoid repository-wide unrelated reformatting. |

## Keep outside the native fork

The e2e companion already owns request routing, protected headers/authentication, provider acquisition/release, state serialization, decoded-PNG mask attestation, recorder/download transfer, secret ledger integration, and fixture lifecycle. Moving those into agent-browser would expand the fork without being needed to maintain the tested boundary. Keep the public `e2e/engine` SPI seam and preserve the existing web/mobile engines.

Dedicated browser ownership remains required. Native target/context scoping is defense in depth, not evidence that a browser shared with unrelated users is safe. Linux proof does not imply macOS full-matrix proof, and synthetic provider fixtures do not prove actual hosted-provider or private-application compatibility.

## Recovery and idempotence limits

The e2e core may intentionally re-observe and relocate after a proven pre-dispatch stale-node failure. That is not the native daemon silently substituting a same-name node after selecting an exact identity. Preserve this distinction in upgrade tests and compatibility claims. At-most-once input dispatch is not exactly-once business operation execution; page handlers and network retries are outside that guarantee.

## Removal rule

For each patch family, record its upstream base, fork commit(s), contract identifier, native test names, consumer integration tests, upstream issue/PR when one exists, and retirement condition. Remove a family only when the selected upstream commit passes the same positive and negative tests and the consumer lock can select it without weakening behavior. An upstream merge, similarly named option, or reduced diff size alone is not a retirement criterion.
